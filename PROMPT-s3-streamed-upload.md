# Промпт: стриминговая заливка объекта в S3

Работа целиком в `MyJetTools/my-s3`. В `fl-url` и `my-http-client` всё готово —
разделы ниже описывают, что там уже есть и на что можно опереться.

## Что уже работает

`my-http-client` (tag `0.1.2`, коммит `07598f09`):

- `MyHttpHyperClient::do_streamed_request(req, timeout)` — запрос с телом, которое
  реализует `hyper::body::Body<Data = Bytes>`. Одна попытка, без ретраев.
- `RequestBodyStream::new(buffer) -> (RequestBodyPublisher, RequestBodyStream)` — тело
  поверх `tokio::sync::mpsc`. Бэкпрешер даёт канал: `publish` ждёт, когда очередь
  забита `buffer` кусками. Дроп паблишера завершает тело.

`fl-url` (эта ветка):

- `FlUrl::put_request_streamed(body)` (а также `post_` / `patch_`) — запрос со
  стримовым телом. Подробности в разделе «fl-url: готово» ниже.

### Измеренные факты (`tests/streamed_request_body.rs`, не предположения)

**1. Явный `Content-Length` вытесняет chunked.** `RequestBodyStream` намеренно не
отдаёт `size_hint`, поэтому по умолчанию hyper фреймит тело как
`Transfer-Encoding: chunked`. Но заголовок, выставленный вызывающей стороной,
побеждает то, что тело говорит о себе. Дамп с провода при
`.with_header("Content-Length", "524288")`:

```
POST /upload HTTP/1.1
content-length: 524288
host: 127.0.0.1:57089
```

`Transfer-Encoding` отсутствует, тело на проводе — ровно 524288 байт, побайтово целое.

**Это и есть то, что нужно S3:** SigV4 не принимает chunked, и отдельный вариант тела
с точным `size_hint` для этого не требуется.

**2. Недобор байт — ошибка запроса, а не молча обрезанное тело.** Если объявить
`Content-Length: N`, а опубликовать меньше, hyper обрывает запись:
`MyHttpClientError::CanNotExecuteRequest("user body write aborted")`. Сервер не получит
усечённый объект под подписью, которая ему не соответствует.

**3. Память константна.** 256 МиБ через локальный сокет — RSS вырос на 5 МБ.

## my-http-client: изменений не нужно

Отдельный вариант тела с точным `size_hint` (он же `MyRequestBody::Streamed`, он же
pull-ридер поверх `AsyncRead`) не нужен: заголовок делает ту же работу, а поведение при
рассинхроне длины уже правильное. Не трогаем.

---

## fl-url: готово

- `post_request_streamed` / `put_request_streamed` / `patch_request_streamed` —
  принимают что угодно с `hyper::body::Body<Data = Bytes>`.
  **PutObject — это PUT**, то есть нужен `put_request_streamed`.
- Режим принудительно `Http1Hyper`. `.compress()` отбивается ошибкой,
  `.with_retries(n)` игнорируется (попытка одна), `.set_timeout` покрывает весь аплоад.
- `Content-Length` ставится обычным `.with_header(...)` — см. факт 1 выше.

Хелпера, который сам читает файл и ставит `Content-Length`, в fl-url **нет**: насос
из `AsyncRead` в `RequestBodyPublisher` пишется на стороне my-s3 (десяток строк, см.
раздел 3). Если окажется, что он нужен в fl-url — скажи, добавлю.

## my-s3: собственно работа

### 1. `x-amz-content-sha256` — главный вопрос

SigV4 требует в этом заголовке SHA-256 тела. Тело, которое ещё не прочитано,
захешировать нельзя. Два варианта, выбрать надо осознанно:

**(а) `UNSIGNED-PAYLOAD`.** Один проход по файлу, самое простое. Подпись покрывает
метод, путь, query и заголовки, но не тело. Допустимо по HTTPS и широко используется;
по HTTP — нет, потому что тело тогда никак не защищено.

**(б) Два прохода по файлу.** Первый — только чтобы посчитать SHA-256 (константная
память, файл в память не читается), второй — сама заливка стримом. Подпись покрывает
тело полностью. Цена — двойное чтение с диска, но пик памяти по-прежнему константный.

Третий вариант из спеки — `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` с `aws-chunked` —
это собственный чанкинг AWS **поверх** HTTP `Content-Length`, с подписью на каждый
кусок. Не путать с HTTP chunked. Реализовывать не предлагаю: заметно больше кода
ради того, что вариант (б) даёт двойным чтением.

### 2. Заголовки

- `Content-Length` = размер объекта, и он должен попасть в `SignedHeaders`.
- `Transfer-Encoding` не добавлять ни при каких условиях.
- `Content-Type` — как сейчас.

### 3. `put_object`

Сейчас сигнатура заставляет держать объект в `Vec<u8>`:

```rust
FlUrl::put(HttpRequestBody::from_raw_data(content, None))
```

Нужен путь, принимающий `AsyncRead` + длину (или путь к файлу), и уходящий в
`put_request_streamed`. Старая сигнатура остаётся для мелких объектов — для них
буферизация проще и дешевле.

### 4. Multipart Upload

Обходной путь через `CreateMultipartUpload` / `UploadPart` / `CompleteMultipartUpload`
перестаёт быть нужен **ради памяти** — однократный PUT теперь работает при константной.
Но остаётся нужен как таковой: у одного PUT в S3 лимит 5 ГиБ, выше него multipart
безальтернативен. То есть его не выкидывать, а перестать выбирать его для объектов,
которые просто «большие для памяти».

Заодно исчезает необходимость в логике отмены (`AbortMultipartUpload`) на этом пути —
недозалитых частей, которые лежат в бакете и стоят денег, при однократном PUT не
бывает.

### 5. Таймаут

`FlUrl::set_timeout` теперь покрывает весь аплоад, а не только ожидание заголовков
ответа. Дефолт 10 секунд для 260-мегабайтного архива не годится — выставлять исходя
из ожидаемого объёма и полосы.

## Как проверить

1. **Против настоящего S3 (или MinIO).** Залить объект заведомо больше лимита памяти
   контейнера и скачать обратно, сверив ETag/SHA-256. Это единственная проверка, которая
   что-то говорит про SigV4.
2. **Память.** Тот же сценарий с ограничением памяти процесса
   (`docker run -m 512m` или `ulimit -v`), объект ~260 МБ — то, на чём падал
   `my-sb-persistence`. RSS не должен расти по размеру объекта.
3. **Фрейминг.** Локальный сокет вместо S3: `Content-Length` присутствует ровно один
   раз и равен размеру объекта, `Transfer-Encoding` отсутствует. В fl-url это уже
   покрыто (`an_explicit_content_length_replaces_the_chunked_framing`), в my-s3 стоит
   повторить на уровне собранного запроса, потому что тут легко потерять заголовок
   при пересборке подписи.
4. **Недобор.** Файл, который усечён между вычислением длины и заливкой: запрос обязан
   упасть, а не залить обрезанный объект.
